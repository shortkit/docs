`replaceFeedItems` replaces the trailing portion of a custom feed queue: the items the viewer has not yet reached. Everything before the boundary is preserved, including the item currently playing.

Use it to revise upcoming content while the feed is in use — to apply updated recommendations, to reflect a user action, or to correct a ranking decision after playback has begun.

`setFeedItems` replaces the entire queue and `appendFeedItems` adds to the end. Use `replaceFeedItems` when the viewer's position must be preserved.

This operation requires a custom feed. Set `feedSource` to custom first — see [Configuration](/sdk/configuration) and [Custom feed input](/guides/content-types#custom-feed-input).

## Boundary resolution

Every call takes a boundary: the last item to keep. Everything after it is replaced.

| Boundary | Keeps | Resolved |
| --- | --- | --- |
| `unseen` (default) | Everything the viewer has reached | At apply time |
| `afterCount` | The current item plus the next `keepUpcoming` items | At apply time |
| `afterItem` | Everything through the item id you supply | At call time |

Resolution time determines which boundary to use. `unseen` and `afterCount` resolve the boundary when the replacement is applied, so it reflects the viewer's position at that moment. `afterItem` resolves it when you call, against the queue as it was then.

<Warning>
**Prefer a relative boundary for server-computed replacements.**

The viewer continues scrolling while a network request is in flight. With `afterItem`, the named item can fall behind the playhead before the replacement is applied, and the call is rejected with `boundary_behind_current`. The rejection rate scales with latency: frequent over mobile connections, rare over a local network, which makes it straightforward to miss during development.

Use `afterCount` or `unseen` for boundaries computed on your server. Use `afterItem` only when a specific item must be the cut point and your code handles rejection.
</Warning>

`afterItem` also accepts an optional `untilId` to bound the end of the range, replacing a window rather than the entire tail.

<Warning>
**`afterCount` counts queue entries, including ad slots.**

`keepUpcoming` indexes `itemIds` directly, so an ad slot between the viewer and the boundary consumes one of the N. For an organization with ads enabled this makes the mode diverge by platform: Android places an ad slot after every fifth video in a custom feed, while iOS places none. The same `keepUpcoming: 2` can therefore keep one of your posts plus one ad slot on Android, and two of your posts on iOS.

If you need a guaranteed number of your own posts ahead of the viewer, count your own ids in `itemIds` and use `afterItem`, or use `unseen`.
</Warning>

## Usage

<Tabs>
  <Tab title="iOS">
    ```swift RecommendationRefresh.swift
    feedVC.replaceFeedItems(
        [
            .video(playbackId: "Xw5BJN2tZkM4q7vLdR9c"),
            .video(playbackId: "f8RkQ01dWcP3mY6aT2hs"),
        ],
        boundary: .afterCount(keepUpcoming: 2)
    ) { result in
        guard result.status == "applied" else {
            print("replace rejected: \(result.reason ?? "unknown")")
            return
        }
        print("kept \(result.keptCount), inserted \(result.insertedCount)")
    }
    ```

    `boundary` defaults to `.unseen`. The remaining cases are `.afterCount(keepUpcoming:)` and `.afterItem(afterId:untilId:)`.
  </Tab>

  <Tab title="Android">
    ```kotlin RecommendationRefresh.kt
    feedFragment.replaceFeedItems(
        items = listOf(
            FeedInput.Video(playbackId = "Xw5BJN2tZkM4q7vLdR9c"),
            FeedInput.Video(playbackId = "f8RkQ01dWcP3mY6aT2hs"),
        ),
        boundary = ReplaceBoundary.AfterCount(keepUpcoming = 2),
    ) { result ->
        if (result.status != "applied") {
            Log.w("Feed", "replace rejected: ${result.reason}")
            return@replaceFeedItems
        }
        Log.d("Feed", "kept ${result.keptCount}, inserted ${result.insertedCount}")
    }
    ```

    `boundary` defaults to `ReplaceBoundary.Unseen`. The remaining variants are `ReplaceBoundary.AfterCount(keepUpcoming)` and `ReplaceBoundary.AfterItem(afterId, untilId)`. The method may be called from any thread; the SDK dispatches to the main thread.
  </Tab>

  <Tab title="React Native">
    ```tsx RecommendationRefresh.tsx
    const result = await feedRef.current?.replaceFeedItems(
      [
        { type: 'video', playbackId: 'Xw5BJN2tZkM4q7vLdR9c' },
        { type: 'video', playbackId: 'f8RkQ01dWcP3mY6aT2hs' },
      ],
      { mode: 'afterCount', keepUpcoming: 2 },
    );

    if (result?.status !== 'applied') {
      console.warn('replace rejected:', result?.reason);
    } else {
      console.log(`kept ${result.keptCount}, inserted ${result.insertedCount}`);
    }
    ```

    `options` is optional and defaults to `{ mode: 'unseen' }`. The full shape:

    ```ts
    type ReplaceFeedItemsOptions =
      | { mode?: 'unseen' }
      | { mode: 'afterCount'; keepUpcoming: number }
      | { mode: 'afterItem'; afterId: string; untilId?: string };
    ```
  </Tab>
</Tabs>

## Queue state

`getFeedQueueState` returns the queue as it currently stands: the ordered item ids, the viewer's position, and the deepest item reached. Use it to compute a boundary, or to reconcile the outcome of a call.

| Field | Description |
| --- | --- |
| `itemIds` | Ordered ids of the items in the queue, including any ad slots |
| `currentIndex` | Index of the item on screen |
| `currentItemId` | Id of the item on screen, or null before any content exists |
| `deepestSeenItemId` | Furthest item the viewer has reached, or null |

<Tabs>
  <Tab title="iOS">
    ```swift
    let state = feedVC.feedQueueState()
    print("\(state.itemIds.count) items, viewer at \(state.currentIndex)")
    ```
  </Tab>

  <Tab title="Android">
    ```kotlin
    val state = feedFragment.feedQueueState()
    Log.d("Feed", "${state.itemIds.size} items, viewer at ${state.currentIndex}")
    ```
  </Tab>

  <Tab title="React Native">
    ```tsx
    const state = await feedRef.current?.getFeedQueueState();
    console.log(`${state?.itemIds.length} items, viewer at ${state?.currentIndex}`);
    ```

    A feed that is not mounted resolves immediately with an empty snapshot.
  </Tab>

## Result fields

A replacement either applies in full or leaves the queue unchanged. There is no partial state.

| Field | Description |
| --- | --- |
| `status` | `applied` or `rejected` |
| `reason` | Present only when rejected |
| `boundaryId` | The last item kept. For `unseen`, this reports the item the SDK selected |
| `keptCount` | Items kept, up to and including the boundary |
| `removedCount` | Items removed from the replaced range |
| `insertedCount` | Items actually inserted |
| `droppedIds` | Incoming items that never entered the queue |

### Dropped items

`insertedCount` can be lower than the number of items supplied. Items the feed refused are listed in `droppedIds`, identified by `id` where set and by `playbackId` otherwise. An item is dropped when it duplicates one already in the queue, or when it carries no usable playback reference.

Compare `insertedCount` against the number of items sent, and read `droppedIds` when the two differ. Refused items are always reported.

## Rejection reasons

| Reason | Meaning |
| --- | --- |
| `feed_not_ready` | The feed is not registered, is empty, is not a custom feed, or its view was torn down |
| `boundary_not_found` | `afterId` was not present in the queue at apply time |
| `until_not_found` | `untilId` was supplied but was not present in the queue |
| `until_not_after_boundary` | `untilId` resolved at or before `afterId` |
| `boundary_behind_current` | The boundary fell behind the item on screen |
| `superseded` | The queue was reset between the call and the apply |
| `invalid_items` | None of the items carried a usable playback reference |

`superseded` warrants explicit handling. It indicates that the queue was replaced between the call and the apply, either by a pull-to-refresh or by your own `setFeedItems`. The replacement was discarded rather than applied to a queue that no longer existed. Re-read the queue state to determine whether the replacement remains appropriate.

<Warning>
**Results differ if the surface is torn down during apply.**

If the feed is dismissed while a replacement is being applied, iOS resolves `rejected` with `feed_not_ready`, while Android resolves `applied`, because the change is applied to the queue and persists. Do not treat the two results as equivalent in this case; call `getFeedQueueState` to establish the outcome.
</Warning>
